# Samsung QN90B — SMACK Policy Write-up

*Target: `root@192.0.2.10` · Tizen 6.5.0 · kernel 5.4.77 · pulled 2026-11-04 (read-only)*

---

## 0. TL;DR

The TV enforces **SMACK** (Simplified Mandatory Access Control Kernel) as its
mandatory access control system. The full policy is **6 929 live access rules**
in the kernel covering **815 unique labels** — 383 of them per-application
(`User::Pkg::*`) sandboxes created by Tizen's *security-manager* at package
install time. Static boot policy lives in `/etc/smack/accesses.d/` (104 rules in
3 files); everything else is generated per installed app and loaded by
`security-manager-rules-loader` at boot.

Raw copies of everything pulled from the TV live in this repo:

| Local copy | Source on TV |

| [`smack/etc-smack/accesses.d/`](../smack/etc-smack/accesses.d/) | `/etc/smack/accesses.d/` — static boot rules |
| [`smack/etc-smack/netlabel.d/`](../smack/etc-smack/netlabel.d/) | `/etc/smack/netlabel.d/` — static netlabel config |
| [`smack/kernel/load2.dump`](../smack/kernel/load2.dump) | `/sys/fs/smackfs/load2` — **full live ruleset** (6 929 rules) |
| [`smack/kernel/cipso2.dump`](../smack/kernel/cipso2.dump) | `/sys/fs/smackfs/cipso2` — live CIPSO network label map (827 entries) |
| [`smack/kernel/netlabel.dump`](../smack/kernel/netlabel.dump) | `/sys/fs/smackfs/netlabel` + `ipv6host` — live netlabel rules |
| [`smack/kernel/settings.txt`](../smack/kernel/settings.txt) | `/sys/fs/smackfs/*` — runtime settings snapshot |

> `/etc/smack/cipso.d/` exists but is **empty** on this unit.

## 1. SMACK in 30 seconds

SMACK attaches an ASCII **label** to every process and every object (files, IPC,
sockets, tasks). A process with **subject** label `S` can touch an object with
**object** label `O` only if:

1. `S` is `^` (hat) and the access is read/execute — allowed,
2. `O` is `_` (floor) and the access is read/execute — allowed,
3. `O` is `*` (star) — any access allowed,
4. `S == O` — any access allowed,
5. an explicit rule `S O <access>` is loaded in the kernel — allowed as specified,
6. otherwise **denied** (and logged; `logging = 1`).

Access mode letters: `r` read · `w` write · `x` execute · `a` append ·
`t` transmute · `l` lock · `-` placeholder/deny. Rules are loaded by writing
`subject object access` lines to `/sys/fs/smackfs/load2`; there can be only one
rule per subject/object pair (last write wins).

File labels are stored in the `security.SMACK64` xattr (plus `SMACK64EXEC` for
domain transitions on exec, `SMACK64TRANSMUTE` for label inheritance on
directory creates, `SMACK64MMAP`, `SMACK64IPIN/OUT` for sockets). A process
label is visible in `/proc/<pid>/attr/current` (or `ps -Z`).

## 2. How policy gets loaded at boot

The TV does **not** use systemd for this; it's a classic init script chain:

```
/etc/init.d/smack_apply
  ├─ mount -t smackfs smackfs /sys/fs/smackfs -o smackfsdef=*   # default label for unlabeled files = *
  ├─ /bin/smackload /etc/smack/accesses.d/default-ac-domains   # static base domain rules
  ├─ echo 2 > /sys/fs/smackfs/mode                            # "SMACK enforce"
  ├─ echo 1 > /sys/fs/smackfs/ptrace                          # exact ptrace policy
  └─ /etc/rc.d/init.d/smack_apply_app &
       ├─ /usr/sbin/cynara-launcher &          # runtime privilege checker (D-Bus gatekeeper)
       ├─ /usr/bin/security-manager-rules-loader
       │    (fallback: dd /opt/var/security-manager/rules-merged/rules.merged → /sys/fs/smackfs/load2)
       ├─ sqlite3 integrity check + recovery of /opt/dbspace/.policy.db      # privilege-checker
       ├─ security DB rollback/recovery of /opt/dbspace/.security-manager.db # per-app rules source
       ├─ /usr/sbin/security-manager-launcher &
       └─ /usr/bin/smack-logger &              # logs SMACK denials to /opt/var/log/smack
```

So the live ruleset is the sum of:

* `default-ac-domains` (83 rules) — loaded first by `smackload`,
* **per-app rules generated by security-manager** from its database
  (`.security-manager.db`), describing every installed package,
* `home-smack` (10 rules) and `lib-softapprovider-tv` (11 rules) — merged in by
  the security-manager loader from `/etc/smack/accesses.d/`.

Notes:

* `smackload` only ever loads `default-ac-domains` directly; the other two
  `.d` files reach the kernel through security-manager's merge.
* `/etc/smack/netlabel.d/netlabel_config` (`0.0.0.0/0 System`) is applied as a
  netlabel rule (see §7).
* Tools present on the TV: `/bin/smackload`, `/usr/bin/smackctl`,
  `/usr/bin/smackaccess`, `/usr/bin/smackcipso`, `/usr/bin/smack-logger`,
  `chsmack`, `cynara-launcher`, `security-manager-*` (all part of the
  `libsmack`/security-manager stack).

## 3. Runtime configuration (live `/sys/fs/smackfs` snapshot)

| Setting | Value | Meaning |
|---|---|---|
| `mode` | `2` | **Vendor extension** — not in upstream smackfs. The boot script writes `2` under the comment `# SMACK enforce`, i.e. MAC enforcement on. (Upstream Smack has no `mode` node; Samsung's kernel also exposes `unconfined-label` instead of upstream's `unconfined` and drops `load-self`.) |
| `ptrace` | `1` | *Exact*: `PTRACE_ATTACH` only between identical labels; `PTRACE_READ` unaffected; `CAP_SYS_PTRACE` can override. |
| `ambient` | `System::Privileged` | Label given to **inbound unlabeled network packets**. (Upstream default is `_`; the TV raises this.) |
| `syslog` | `*` | Any label may use syslog. |
| `logging` | `1` | Log **denied** accesses (audit via kernel log / `smack-logger`). |
| `onlycap` | *(empty)* | `CAP_MAC_ADMIN` / `CAP_MAC_OVERRIDE` are effective for **any** label — no only-capable label restriction. |
| `unconfined-label` | *(empty)* | No unconfined (bring-up) label configured. |
| `relabel-self` | *(empty)* | No self-relabel whitelist; relabeling requires `CAP_MAC_ADMIN`. |
| `revoke-subject` | *(empty)* | No subject label revoked. |
| `doi` | `3` | CIPSO Domain Of Interpretation (upstream default). |
| `direct` | `250` | CIPSO level meaning "the categories encode the label itself" (labels < 24 chars). |
| `mapped` | `251` | CIPSO level meaning "the categories encode the label's secid" (labels ≥ 24 chars). |

Practical consequence of `onlycap` being empty: **our root shell (label `User`,
full capabilities) can read and write the whole SMACK policy live**
(`load2`, `change-rule`, `revoke-subject`, …) — including revoking rules
without touching any on-disk file. Verified hands-on in §9.

## 4. The domain model

The static policy implements Tizen's **three-domain model** plus TV-specific
extensions. The labels and their roles:

**Predefined system labels**

| Label | Name / role |
|---|---|
| `_` | **floor** — anyone may read/execute floor objects |
| `*` | **star** — anyone may access star objects; star processes may access nothing (also the mount default for unlabeled files here) |
| `^` | **hat** — may read/execute anything |
| `!` | appears in the CIPSO map only |

**Base domains** (from `default-ac-domains`)

| Label | Role |
|---|---|
| `System` | core system services & their data |
| `System::Log` | log files (`/var/log`, `/opt/var/log`) |
| `System::Run` | runtime state (`/run`) |
| `System::Shared` | system-writable shared data |
| `System::Tools` | diagnostic/debug binaries & tools |
| `System::Privileged` | privileged platform services (Tizen's "root service" domain — 46 processes run here) |
| `System::Privilege::Internet` | *gate object* for internet access (D-Bus privilege proxy) |
| `System::Privilege::AppDebugging` | *gate object* for app debugging |
| `System::TEF` | TEF framework/services glue domain (present only in the static base policy; expansion not documented anywhere on the unit) |
| `User` | user-facing apps & user data |
| `User::Shell` | developer/CLI shell domain (our SSH shell runs as `User`) |
| `User::Home` | `/home` user data |
| `User::App::Shared` | app-shared data directory |
| `User::Pkg::<appid>` | per-application sandbox (one per installed package) |
| `User::Pkg::<appid>::RO` | per-app read-only resource directory |
| `User::Author::<sha>` | data shared between apps of the same signing author |
| `User::App` | legacy/shared app label (one rule set) |

**TV-specific service labels** (lowercase, added by `lib-softapprovider-tv` and
visible in the live ruleset): `dbus`, `connman`, `wpasupplicant`,
`tethering::dbus-access`, `secure-storage::tethering`, `system::use_internet`,
`system::vconf`, `system::homedir`, `system::dtv-vddebugmenu`,
`dtv-softap-provider`.

## 5. Static boot policy (`/etc/smack/accesses.d/`)

### 5.1 `default-ac-domains` — the base 83 rules

Who can do what between the base domains (complete file:
[`smack/etc-smack/accesses.d/default-ac-domains`](../smack/etc-smack/accesses.d/default-ac-domains)).
Condensed:

| Subject | Object | Access | Purpose |
|---|---|---|---|
| `System` | `_`, `^`, `User`, `System::Privileged`, `System::Tools`, `System::Log` | `rwxa` / `rwxat` / `r-x` | the System domain can act on everything: read/write floor & star, write to user, run tools, write logs |
| `System` | `User::App::Shared`, `User::Home`, `System::Run`, `System::Shared` | `rwxat` | transmute-enabled shared dirs |
| `System` | `System::Privilege::Internet`, `System::Privilege::AppDebugging` | `-w----` | **privilege gates**: write (send D-Bus request) to the gate |
| `_` | `System::Run`, `System` | `rwxat` / `-wx---` | floor may create in `/run`, write to System |
| `_` | `System::Privilege::Internet`, `System::Privilege::AppDebugging`, `System::Privileged`, `System::Tools` | `-w`/`-wx`/`r-x` | floor services can reach privileged gates |
| `System::Privilege::Internet` | `_`, `System::TEF`, `System::Privileged`, `System`, `User`, `User::Shell` | `-w----` | the internet gate may write back to processes (granted responses) |
| `System::Privilege::AppDebugging` | same six | `-w----` | same pattern for the debugging gate |
| `System::TEF` | `System`, `System::Privileged`, `System::Run`, `System::Shared`, `User::Home`, `User::App::Shared` | `rwxat` | TEF framework is fully privileged |
| `System::TEF` | `_` | `rwx` | …and can touch floor data |
| `System::Privileged` | everything `System`/`System::TEF` touches + `^`, `User`, `User::Shell` | `rwxa(t)` | privileged platform services are the most powerful non-`System` domain |
| `User::Shell` | `User::Home`, `System::Run`, `System::Shared` | `r-x--l` | shell may browse user/system runtime data, lock files |
| `User::Shell` | `User::App::Shared` | `rwxat` | shell can write shared app data |
| `User::Shell` | `System::Log`, `System::Privilege::Internet`, `System::Privilege::AppDebugging` | `-w----` | shell can request internet/debugging privileges |
| `User::Shell` | `User`, `System` | `-wx---` | shell can write to user/system (e.g. start apps, install) |
| `User::Shell` | `System::Tools` | `r-x---` | shell can execute tools |
| `User` | `User::Home`, `User::App::Shared`, `System::Run` | `rwxat` | user apps own their shared dirs |
| `User` | `System::Log`, `User::Shell` | `rwxa` / `rwxat` | apps write logs, talk to shell |
| `User` | `System::Privilege::Internet`, `System::Privilege::AppDebugging` | `-w----` | apps request privileges through the gates |
| `User` | `System::Shared` | `r-x--l` | apps read shared system data |
| `User` | `System::Privileged`, `System`, `User`, `System::Tools` | `-wx`/`r-x` | apps write to services, execute tools |
| `^` | `System::Log`, `System::Run`, `System::Privileged`, `System` | `rwxat`/`rwxa` | hat domain is trusted |
| `_` | `User::Home`, `User::App::Shared`, `System::Shared`, `System::Log` | `-----t` | **transmute-only**: floor processes creating files in transmuting dirs inherit the dir's label |

The defining trick is the **privilege-gate pattern**: apps never get
`System::Privilege::Internet` as a subject label. Instead the gate object is
write-only for everyone; a privileged daemon (cynara/security-manager) checks
the request and performs the action on the app's behalf. Removing an app's
internet access never requires touching SMACK — it's a D-Bus/cynara decision.

### 5.2 `home-smack` — 10 rules (no trailing newline in the file)

Bidirectional read-write-append-transmute between the CSFS service
(`com.samsung.tv.csfs`) and the five Smart Hub "home" sub-apps:

```
User::Pkg::com.samsung.tv.csfs  ⇄  com.samsung.tv.home.media
User::Pkg::com.samsung.tv.csfs  ⇄  com.samsung.tv.home.sidebar
User::Pkg::com.samsung.tv.csfs  ⇄  com.samsung.tv.home.game
User::Pkg::com.samsung.tv.csfs  ⇄  com.samsung.tv.home.work
User::Pkg::com.samsung.tv.csfs  ⇄  com.samsung.tv.home.art
```

(all `User::Pkg::*` labels, access `rw-at-`). This lets the home screen
components share media/sidebar/game/work/art content through the CSFS broker.

### 5.3 `lib-softapprovider-tv` — 11 rules

Grants the **soft-AP (tethering/WiFi-direct) provider** the labels it needs:

| Subject | Object | Access |
|---|---|---|
| `dtv-softap-provider` | `secure-storage::tethering` | `rw----` |
| `dtv-softap-provider` | `system::dtv-vddebugmenu`, `system::homedir`, `system::vconf` | `rwxat-` |
| `dtv-softap-provider` | `system::use_internet`, `wpasupplicant`, `tethering::dbus-access`, `connman`, `dbus` | `rwx---` |
| `system::use_internet`, `dbus` | `dtv-softap-provider` | `rwx---` |

### 6.2 Per-app sandbox pattern (security-manager generated)

Every installed package `<appid>` gets a deterministic block of **12 baseline
rules**, identical in shape for every app. Example — the sideloaded Kodi
(`org.xbmc.kodi`):

```
User::Pkg::org.xbmc.kodi  User::Pkg::org.xbmc.kodi          rwxat   # own data dir: full access + transmute
User::Pkg::org.xbmc.kodi  User::Pkg::org.xbmc.kodi::RO      rxl     # own read-only resources
User::Pkg::org.xbmc.kodi  User::Author::2baede37b52bfdd8    rwxat   # data shared with same-signed apps
User::Pkg::org.xbmc.kodi  User::App::Shared                 rwxat
User::Pkg::org.xbmc.kodi  User::Home                        rxl
User::Pkg::org.xbmc.kodi  User                             wx
User::Pkg::org.xbmc.kodi  System::Log                       rwxa
User::Pkg::org.xbmc.kodi  System::Run                      rwxat
User::Pkg::org.xbmc.kodi  System::Shared                   rxl
User::Pkg::org.xbmc.kodi  System::Privileged               wx
User::Pkg::org.xbmc.kodi  System                          wx
User::Pkg::org.xbmc.kodi  _                                l       # may lock floor objects (databases etc.)
```

Apps with more than 12 rules have **cross-app sharing** extensions, nothing
else. Example `com.samsung.tv.csfs` (17 rules): the 5 extra rules are exactly
the `home-smack` grants toward the five `home.*` apps (`rwat` — the `-`
placeholders from the file are normalized away in the kernel's rule
representation). There are **no privilege-specific SMACK rules for apps**: no
app holds a direct `System::Privilege::Internet`, `System::Privilege::AppDebugging`
or `system::use_internet` rule (the latter belongs solely to
`dtv-softap-provider`). App privileges (internet, debugging, …) are enforced at
the D-Bus/cynara layer, not in SMACK — consistent with the gate model in §5.1.

Interesting edge cases in the generated matrix: `User::Pkg::org.tizen.sso-profile`
appears as a subject but has no self-rule, and `User::Pkg::SSO_ADMIN` exists only
as an object — leftovers of the SSO profile/admin split that don't fit the
baseline pattern (the cipso map even references a third variant,
`User::Pkg::xvvl3S1bvH`, that has no access rules at all — a stale label from an
app update). Otherwise the pattern is exact: 382 apps with a complete
self + `::RO` + author sandbox block.

Interesting author-label distribution: `User::Author::fb0d6add0fa9aff9` (the
platform signing author) is granted to **204 app subjects** (plus the three
launcher domains `System`, `System::Privileged`, `User`) — all Samsung-signed
apps share data signed under the same author hash. The 24 author hashes include
one shared by the two sideloaded apps (`2baede37b52bfdd8`, used by
`org.xbmc.kodi` and `xvvl3S1TT1`), i.e. apps signed with the same developer
certificate can share author-labeled data.

### 6.3 Launcher / platform domains

The three super-subjects each hold ~800 rules: **788 of them** are per-app
grants — for each of the 382 installed apps, one rule toward its data label and
one toward its `::RO` label (both `rwxat`), plus 24 rules toward every
`User::Author::*` label — with the remainder being their base-domain rules
from `default-ac-domains` (13 for `System`/`System::Privileged`, 11 for `User`):

| Subject | Rules | Purpose |
|---|---|---|
| `System::Privileged` | 801 | platform services can read/write every app's sandbox (app management, backup, security-manager itself) |
| `System` | 801 | same reach from the core System domain |
| `User` | 799 | the app launcher ("User" domain) can enter every app's sandbox to start/stop apps |

These counts track the installed-app inventory exactly (they shrink/grow with
package installs via security-manager).

| Label | Processes | Who |
|---|---|---|

## 7. Network labeling (CIPSO & netlabel)

### 7.1 Live netlabel rules (`/sys/fs/smackfs/netlabel`)

```
127.0.0.1/32 -CIPSO      # loopback: treated as a CIPSO-capable host (standard CIPSO)
0.0.0.0/0    System      # everything else: single-label host "System"
```

Effect (longest-mask-first matching):

* **Outbound** packets to non-loopback hosts are sent **unlabeled**, but only
  from processes that have *write* access to `System`. Note that every app's
  baseline block includes `User::Pkg::<app> System wx` (§6.2), so effectively
  **all app domains can emit packets to the internet** — per-app network
  privilege enforcement happens at the cynara/D-Bus gate layer, not here.
* **Inbound** packets from the outside world are labeled `System`.
* Unlabeled packets not matching any netlabel entry get the **ambient label**
  — here `System::Privileged` (matters mostly for IPv6, since `0.0.0.0/0`
  covers all IPv4).

`ipv6host` is empty (no IPv6 single-label hosts configured).

### 7.2 CIPSO map (`/sys/fs/smackfs/cipso2`, 827 entries)

Every live label has a CIPSO encoding so that labels survive the loopback
trip through IP:

* **61 labels** use level **250 (direct)** — the label text itself is encoded
  in the category bitmap (short labels, < 24 chars): e.g. `dbus`,
  `connman`, `!`, `wifi_direct_manager`, `soc-pba-interface`.
* **766 labels** use level **251 (mapped)** — the label's numeric *secid* is
  encoded (long labels ≥ 24 chars): all `User::Pkg::*`,
  `User::Author::*`, …
* DOI is **3**.

Example entries:

```
User::Pkg::org.xbmc.kodi::RO 251/3,4,5,6,15,16
dtv-org.tizen.emanual-app    251/3,4,5,15,16
!                            250/3,8
```

## 8. Notes for debloating / hacking

* **Removing an app does not immediately remove its rules.** The 6 929 rules
  live in the kernel until reboot; security-manager regenerates them at boot
  from `/opt/dbspace/.security-manager.db`. Uninstalling a package properly
  (pkgmgr) updates that DB; forcibly deleting files leaves stale rules until
  the next `security-manager-rules-loader` run.
* Stale-but-loaded rules are harmless (a rule for a label no process or file
  carries can never match), which is why debloat-by-file-deletion doesn't
  break the MAC policy.
* The static files are tiny — the real policy is the **generated per-app
  matrix**. If you want a "before/after" diff of a debloat session, re-dump
  `load2` and diff: `ssh root@192.0.2.10 cat /sys/fs/smackfs/load2`.

## 9. Live policy surgery as root (verified hands-on)

All of the below was **executed and verified on the unit** (2026-11-04, dummy
labels, cleaned up afterwards). It works because our SSH root shell has
`CapEff = 0x0000003fffffffff` (all capabilities, incl. `CAP_MAC_ADMIN` = 28,
`CAP_MAC_OVERRIDE` = 27) **and `onlycap` is empty** — smackfs write permission
checks nothing beyond `CAP_MAC_ADMIN` + the onlycap list.

### 9.1 What works (commands as run on the unit)

| Operation | Command | Verified result |
|---|---|---|
| Load rule(s) | `echo "S O rwxat" > /sys/fs/smackfs/load2` (one rule per write; `/bin/smackload file` for batches) | ✓ rule visible in `/sys/fs/smackfs/load2` instantly, enforced immediately |
| Query a pair | `/usr/bin/smackaccess S O <access>` or write+read `access2` | ✓ returns `1`/`0`; **quirk:** the `access2` read must use the *same fd* as the write — a separate `cat` returns empty on this kernel |
| Modify a rule bitwise | `echo "S O <grant> <strip>" > /sys/fs/smackfs/change-rule` | ✓ `rwxat` → `rat` after stripping `wx` |
| Unload one rule | `echo "S O -" > /sys/fs/smackfs/load2` | ✓ rule disappears; **there is no true delete** — only overwrite with deny (zero-access rules are hidden from `load2` reads and can never match) |
| Bulk unload a subject | `echo "S" > /sys/fs/smackfs/revoke-subject` | ✓ all rules with that subject label → 0 (sets access to `-`) |
| Relabel own process | `echo "System::Privileged" > /proc/self/attr/current` | ✓ `User` → `System::Privileged` instantly, capabilities unchanged — instant domain escalation to *any* label |
| Relabel any file | `chsmack -a <label> <path>` (also `SMACK64EXEC`, `SMACK64TRANSMUTE`, …) | not exercised; `CAP_MAC_ADMIN` verified present, and per kernel docs `SMACK64EXEC` runs a binary under the xattr's label |

Access strings are normalized by the kernel: `r-x` is reported back as `rx`,
`rw-at-` as `rwat`, etc.

### 9.2 What cannot be unloaded

Kernel built-ins — no rule change can override these:

* **same-label access** is always permitted (can't lock a process out of its
  own label),
* read/execute on **`_` (floor)** objects is always permitted,
* read/execute by **`^` (hat)** subjects is always permitted,
* any access to **`*` (star)** objects is always permitted.

### 9.3 Even without touching rules

`CAP_MAC_OVERRIDE` (which root holds) lets a process **bypass MAC decisions
outright** for most file/IPC accesses — as root we are effectively above the
policy; loading/unloading rules is only needed to change what *other*
(non-privileged) processes may do.

### 9.4 Caveats

1. **Changes are live-only and system-wide.** They bind all ~239 processes
   instantly; removing a rule a running service depends on can break it *until
   reboot* — and reboot is the safety net: boot fully regenerates the policy
   from the security-manager DB, so nothing persists.
2. **No persistence from `/etc/smack`**: the system root is a read-only VDFS
   mount, so the static `.d` files can't be edited. Persisting custom rules
   needs a boot-time hook on a writable mount (e.g. something under `/opt`).
3. **`mode=2`** (the vendor enforce switch) is writable too, but values other
   than 2 are undocumented vendor behavior with system-wide effect — stick to
   per-rule control, which is precise and reversible.
4. `smackfs` writes require `*ppos == 0` (one rule per write syscall) — plain
   `echo … > file` works, appending does not.

### 9.5 Debloat angle

* **Unloading rules is mostly pointless** (see §8 — stale rules are inert).
* **Loading is the interesting direction**: grant a domain extra access, or
  use `chsmack` + `SMACK64EXEC` to run any executable under any label — e.g.
  re-running a "removed" system service under its original domain needs only
  its binary + label, not its package.
* To audit what a tampered service is still trying to access, use
  `smackaccess` queries and the existing denial logging (`logging = 1` →
  kernel log / `smack-logger` → `/opt/var/log/smack`).
